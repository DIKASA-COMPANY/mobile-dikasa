# Refunds and Cancellation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The user requires inline execution without subagents, including review.

**Goal:** Allow outlet cashiers/managers to refund all remaining receipt units or selected item quantities, with an immutable audit trail, exact amounts and optional stock returns.

**Architecture:** Introduce an additive `refund` package using original payment snapshots and refund records. One pure allocation/validation engine serves preview and confirmation; PostgreSQL serializes confirmation, links returned stock to its refund and protects quantity limits. Extend existing paid-history browsing with receipt detail/refund dialogs and matching mock behavior.

**Tech Stack:** Existing Go, GORM/PostgreSQL, Gin/Huma, Flutter/Dart, MobX and Dio. Use Go `math/big` and Dart `BigInt` for allocation intermediates; no new dependencies or external services.

**Spec:** [Approved refund design](../specs/2026-10-24-refunds-design.md). Paths below are relative to the parent `Dikasa` workspace. Backend commands run in `be-dikasa`; Flutter commands run in `mobile-dikasa`.

## Global Constraints

- Work inline, no subagents. Customer management remains deferred.
- Preserve prior uncommitted changes. Keep this work local and uncommitted unless the user separately requests Git integration.
- Whole refund after partial refunds means the remaining balance, not a second refund of the original total.
- The original receipt and sale item snapshots stay intact.
- Stock return defaults to zero. The cashier explicitly chooses returned quantities per line.
- Refund the charged `total_amount`, not `paid_amount`.
- Reason is 1–500 Unicode characters. Item quantities are whole units, no greater than remaining sold quantities; stock-return quantity is 0..selected refund quantity.
- Use original transaction/item snapshots, never current catalog prices or current tax.
- Only authenticated cashier/manager accounts can refund within their own outlet; foreign-outlet receipt/refund IDs return404.
- Require an active outlet cash session at confirmation and record it on the refund, even when the original sale belongs to an older session.
- Money is returned outside this app and recorded by the cashier. No payment gateway transfer is initiated.
- All authenticated routes use `/dikasa/v1` and existing response/error envelopes.
- Same UUID and canonical payload returns the original successful response; changed payload under that UUID returns409.
- Verify migration000011 in temporary schemas before applying only that migration locally; never refund an existing real user sale for a smoke check.
- Update the dated feature log, changelog, feature index, backlog, OpenAPI, Bruno and Draw.io source in this delivery.

## Review Focus

1. An uncertain refund that actually committed must replay after later refunds or cash-session changes; Task 3 tests lookup/replay before mutable-state checks.
2. Original untracked stock enabled today must not become refundable stock; Tasks 2–3 test eligibility from original sale movements, including base/variant aggregation.
3. Free items and one-Rupiah tax budgets must close correctly after several partial refunds; Task 1 tests quantity-based completion and cumulative allocations.
4. A preview must not authorize a different selection/reason/method on confirmation; Tasks 1/4/6 test canonical preview hashes and invalidation after every form change.
5. A late detail/preview/confirm reply after an account switch must not show an old receipt or clear a new cart; Tasks 6–7 exercise all asynchronous boundaries.
